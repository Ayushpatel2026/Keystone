\section{Workflow Plan}

\begin{itemize}

    \item \textbf{Git Usage:} We will primarily be using GitHub for managing the project files.
    The feature branch strategy will be used with each member creating a dedicated branch for each task that they work on.
    This branch can be deleted after the task is completed and merged into the main branch.
    The member should open a pull request after completion of their assigned task. If
    multiple members are collaborating on the same task, they will work within the same branch. Once completed,
    a pull request can be opened which will be reviewed by the other team members.

    \textbf{Overall Workflow Plan}
    \begin{enumerate}
        \item \textbf{Issue Creation:} For each deliverable, we will create many different issues. Each issue equates to a specific task that needs to be completed. An issue could be about multiple related sections of a deliverable or a single modular piece of code functionality.
        \item \textbf{Branching:} Each team member will create a branch for each task that they work on. If multiple members
        collaborate on the same task, they will work on the same branch to avoid merge conflicts.
        \item \textbf{Commit Process:} All changes will be regularly committed to the respective branches. We will follow the Conventional Commits standard (e.g. \texttt{feat:}, \texttt{fix:}, \texttt{docs:}, \texttt{chore:}, \texttt{refactor:}) so that commit history is easy to scan and purposeful. Each commit should represent a single, working, well-documented change -- no commit farming (i.e. no meaningless, placeholder, or "WIP" commits left in the final history). Commit messages should clearly describe \emph{what} changed and, where not obvious, \emph{why}.
        \item \textbf{Pull Requests (PRs):} Once a team member has completed a task, a pull request on GitHub will be created. Directly pushing to the main branch is not allowed.
        A pull request must be created and it must pass all CI checks before it can be merged into the main branch.
        Every PR must include a description. For straightforward or self-explanatory changes, a brief description is sufficient. For changes where the intent, approach, or impact would not be immediately obvious to a reviewer (particularly code changes), the author must provide a more detailed description covering what was changed, why, and any tradeoffs or design decisions made. This makes it much easier for reviewers to understand the changes and provide meaningful feedback.
        \item \textbf{Team Member Review:} The PR will be reviewed by at least one other team member to ensure that all of the rubric criteria has been met.
        If the PR contains code changes, the PR will also be reviewed for code quality and functionality. The reviewer(s) provide feedback through comments. The author
        of the section should respond or implement any feedback provided by the member who reviewed the submission. If a merge conflict arises during review, it is the responsibility of the branch owner to resolve it (or resolved collaboratively if the branch is shared) before requesting re-review.
        \item \textbf{Merging:} Once the PR has been reviewed, approved, and confirmed that all of the rubric criteria has been met, it will successfully
        be merged into the main branch. We will not use squash merging, to ensure that all commits are visible in the main branch. To maintain a linear history, we will use rebase and merge.
        \item \textbf{Definition of Done:} An issue/task is considered complete when: its checklist items are fully addressed, its associated PR has passing CI checks and, where required, at least one approving review and it has been merged into the main branch.
    \end{enumerate}


    \textbf{Branch Protection Rules:}
    To enforce the above process, the following protections will be applied to the main branch:
    \begin{itemize}
        \item No direct pushes to main -- all changes must go through a pull request.
        \item Pull requests must pass all required CI checks before merging.
        \item Code-related pull requests will additionally require review and approval from a designated code owner (at least one of the 4 team members), enforced via a \texttt{CODEOWNERS} file. This file will be created once the project's technology stack has been finalized, so that the file can be made using the relevant language/framework directory structure and file extension.
        \item Non-code files (e.g. documentation, LaTeX files, images) will not have mandatory reviewer approval enforced through branch protection, so that minor changes such as wording fixes, typos, or adding images are not bottlenecked by teammate availability. The team will still follow the PR review process as a best practice for major documentation-related tasks, even where it is not explicitly enforced.
    \end{itemize}


    \textbf{Project Management:}
    We will be using GitHub Issues to keep track of the following items: tasks, meetings, and other important items.
    Each issue will be part of a milestone that corresponds to a specific deliverable (i.e. Problem Statement and Development Plan, SRS, etc.)
    All issues and milestones will be part of a GitHub Project (\href{https://github.com/users/Ayushpatel2026/projects/3}{Keystone Project}) in a Kanban style so we can visualize and track the progress of our project.

    There are template issues readily available from the course instructor, as shown below, and we will be using these throughout our capstone. \\

    \textbf{Issue Templates Available:}
    \begin{itemize}
        \item Lectures: Used to track team details during lectures (i.e. important notes, attendance)
        \item Peer Review: Individuals outside of the team review one of our items
        \item Supervisor Meeting: Agenda template for meetings with supervisors/stakeholders
        \item TA Meeting: Agenda template for meetings with TA
        \item Team Meeting: Agenda template for weekly meetings with our team
        \item Blank Issue: Blank template to be used to create a new issue \\
    \end{itemize}

    \textbf{Issue Labels Classification:}

    Below are the set of labels in GitHub Issues that we will be using when creating issues to organize them:

    \begin{itemize}
        \item Bug: Used for issues that indicate something is not working as expected
        \item Feature: Used for issues that represent any new functionality that provides visible value to users.
        \item TA Meeting: Used for issues that include meeting notes, feedback and actions from TA sessions.
        \item Team Meeting: Used for issues where team meeting discussions are noted.
        \item Supervisor / Stakeholder Meeting: Used for issues where meetings with the project supervisors and stakeholders are documented.
        \item Documentation: Used for issues corresponding to any work related to documentation, including updates to the ReadMe's and latex files.
    \end{itemize}


    \item \textbf{Use of CI/CD:} We will be using GitHub Actions as our CI/CD platform to ensure that all of our documentation and project files are being built,
    formatted, and reviewed properly before they are merged into the main branch of the project. Workflows, which are defined in
    YAML files, will trigger automatically on pushes and pull requests. To ensure consistency across
    all files, merges require both teammate approval (only for code files, using a CODEOWNERS file) and passing CI checks.
    While we will still use the PR review process for all major documentation-related tasks, we will not officially enforce teammate approval for documentation-related PRs, to ensure that we are not bottlenecked by teammate availability for minor changes.
    CI will also run all unit tests to make sure we are not introducing any regressions.
    Checks will be added to ensure linting, code quality analysis, and unit test coverage (see Technology and Coding Standard sections for more details).
    Enforcing CI checks ensures errors are caught early and also ensures we follow industry-standard practices.

\end{itemize}

\section{Coding Standard}

\wss{What coding standard will you adopt?}

The team will follow the coding standards and conventions below to ensure consistency, 
readability, maintainability, and code quality across the project:

\begin{itemize}
    \item \textbf{Python / FastAPI:} Python code should adhere to \textbf{PEP 8}. 
    Ruff is the Python Linter used to enforce these standards and identify common code-quality issues.

    \item \textbf{Typescript / React:} Frontend code will follow consistent Typescript and React conventions 
    for naming, formatting, component structure, and static typing typically enforced by ESLint.
    
    \item \textbf{Software Design/Architectural Principles:} \textbf{SOLID} and \textbf{GRASP} principles 
    should be used to ensure proper design principles are followed such as single responsibility, separation of 
    concerns, high cohesion, low coupling, modularity, abstraction, and extensibility. Following these will allow
    the project to have a maintainable system design.

    \item \textbf{Testing Standards:} Test design should be guided by ISO/IEC/IEEE 29119-4
    to ensure consistent software testing practices based on requirements. The standards cover software testing 
    techniques used to evaluate boundary conditions, edge cases, and expected failure conditions.

    \item \textbf{Statement Coverage:} Automated tests should target approximately 80\% statement coverage for application code. 
    Statement coverage along with test design standards defined above should determine overall desired test quality.

    \item \textbf{Readability and Naming:} Code should use descriptive and consistent names and favour clear, 
    simple implementations over unnecessary complexity. Comments should give high-level implementation explanations.

    \item \textbf{Error Handling:} Failure conditions should be handled explicitly, with clear and consistent error messages.

\end{itemize}

\textbf{Ayush Patel:}

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the
    project?

    This is an 8-month project with 4 team members, and everyone has different experience levels, expectations, and work styles when it comes to project management. It's best to get everyone on the same page early about things like how we're going to use Git and GitHub (branching, issues, milestones, etc.), and what our expectations are around meetings and attendance.

    Documenting all of this early and getting everyone to agree to it means we have something concrete to point back to later if something goes wrong or if someone isn't pulling their weight.

    I also really like the external goals section of the development plan, since everyone has different things they personally want to get out of the capstone, and it's good to be transparent about that early rather than finding out halfway through.

    \item In your opinion, what are the advantages and disadvantages of using
    CI/CD?

    Advantages: regression bugs get caught early and often, on every push to a PR and every merge to master, instead of piling up and surfacing all at once near the deadline.

    Disadvantages: CI can give a false sense of confidence. A green build doesn't necessarily mean everything actually works, it just means your tests passed, and if your tests aren't well designed, a green checkmark can hide real bugs.
    Setting up CI by itself doesn't automatically catch regressions, you still have to actually design your unit, integration, and e2e tests properly so they're checking the functionality that actually matters.
    This is why it is very important to not only run your CI frequently, but also to maintain and update the test suite and other checks that the CI is running.

    \item What disagreements did your group have in this deliverable, if any,
    and how did you resolve them?

    We had a disagreement about what backend language/framework to use.
    Some team members wanted Next.js, but most of us wanted Python because it's easy to use and has great library support if we need it down the line.
    We explained our rationale to the rest of the group and everyone agreed to go with Python.

    We also disagreed on what to use for productivity metrics, things like commit count, number of issues closed, or cumulative issue size.

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the
    project?
    
    Drawing on previous experience, when projects get large enough and has multiple collaborators,
    many points of contention and slow-downs occur as a consequence of the development process itself.
    Differences in code styles, tool usage, quality expectations, workflows, and documentation can
    result in expectations not being met, and issues being raised as a result which need to be resolved
    using reviews, discussions, and meetings, where they weren't needed if expectations were setup properly.
    Creating a development plan from the start can reduce future strain on a project's progress and allow the
    time saved to be spent on improvements and expanding capabilities. 

    \item In your opinion, what are the advantages and disadvantages of using
    CI/CD?

    CI/CD can bring a standard of quality that manual review simply cannot do reliably. Automated tests, static
    analysis tools, and artifact generation can be completed in the background while important tasks such as
    design and implementation receive full focus and attention. CI/CD can raise a notification only when something 
    requires manual intervention (failed test, build, etc.), reducing noise in the development process. While
    CI/CD can bring immense value, CI/CD itself can grow to be a system of its own requiring setup, debugging,
    and cloud costs, all of which is additional overhead that must be justified.

\subsection*{Attendance}

\subsubsection*{Expectations}

\wss{What are your team's expectations regarding meeting attendance (being on
time, leaving early, missing meetings, etc.)?}


\begin{itemize}
    \item 80\% attendance is required for team, TA, and supervisor meetings.
    \item If a member must miss a meeting, they must notify the team in advance and provide a written update covering their progress and any action items relevant to them.
    \item Members attending a meeting are expected to arrive on time (at most 10 minutes late) and stay for its full duration.
    \item \textbf{Trigger:} Missing 2 consecutive meetings, \emph{or} being late thrice in a row, triggers a consequence.
    \item \textbf{Consequence:} the member brings snacks/coffee to the next team meeting for a first occurrence; a second occurrence within the same term triggers a mandatory check-in meeting with the TA to discuss the pattern.
    \item These standards apply to non-emergency cases only (see below for emergencies).
\end{itemize}


\subsubsection*{Acceptable Excuse}

\wss{What constitutes an acceptable excuse for missing a meeting or a deadline?
What types of excuses will not be considered acceptable?}

\begin{itemize}
    \item \textbf{Acceptable:} midterm preparation, conflicting lectures/tutorials, work-related obligations, medical appointments.
    \item \textbf{Not acceptable:} forgetting the meeting, non-urgent personal plans, or repeated last-minute excuses of the same kind. Repeated use of the same excuse will be treated as a pattern and addressed under the "Stay on Track" consequences below.
    \item Advance notice is expected wherever the excuse is foreseeable (e.g. a scheduled appointment).
\end{itemize}


\subsubsection*{In Case of Emergency}

\wss{What process will team members follow if they have an emergency and cannot
attend a team meeting or complete their individual work promised for a team
deliverable?}

\begin{itemize}
    \item In a genuine emergency, the attendance rules above do not apply.
    \item The member should notify the team as soon as reasonably possible.
    \item If the emergency will materially impact a deliverable, there are two options:
    \begin{enumerate}
        \item The other members will redistribute the member's tasks among themselves, and then that team member can pick up more work in future deliverables.
        \item If the rest of the team cannot handle the extra workload, the team will raise it with the TA and/or course instructor proactively, rather than waiting until the deadline is missed.
    \end{enumerate}
\end{itemize}
