  \subsection{Purpose}

  \plt{State the purpose of the system.}

  \plt{The purpose should be in the context of the project itself, not in the
  context of this course. Although the ``purpose'' of the document is to get a
  grade, you should not mention this.  Instead, ``fake it'' as if this is a real
  project.}

  The purpose of \projname{} is to make capstone project proposals, discovery, team formation, and
  team project approval transparent, consistent, and easy to manage for the students, supervisors, and
  course instructors involved.

  \plt{What problem does your program solve?
  The description here should be in the problem space, not the solution space.}

  Capstone project and team selection currently happens across disconnected tools such as email,
  online forms, discussion forums, and shared files, leading to a lack of visibility, clarity, and detail in
  information available to students, supervisors, and instructors. As a result, project descriptions do not set clear
  expectations, students and supervisors cannot easily tell which projects are available or learn about each other, and
  instructors spend significant time manually coordinating the process.
  See \nameref{sec:problem-statement} for a more detailed description of the problem.

  \projname{} is intended to solve these problems by giving every participant a single, trustworthy
  source of information about capstone projects, teams, and their status, from the moment a project
  is proposed until it is approved.

  \subsection{Scope}
  \label{sec:scope}
  \plt{Briefly describe:
    \begin{itemize}
      \item Problem being solved
      \item Intended users
      \item Major functionality
      \item Expected benefits
      \item Clarifying the scope often means saying what the software doesn't do
    \end{itemize}
  }
  \plt{The scope section is relevant for understanding the boundaries of the system. It is also relevant for later determining typical values of inputs. The scope should make it clear what inputs are reasonable to expect. This is a distinction between scope and context (context is a later section).  Scope affects the inputs while context affects how the software will be used.}


\textbf{Problem being solved.} The fragmented and unreliable flow of information in capstone
  project and team selection and approval, as described in the \nameref{sec:problem-statement} section below.

  \textbf{Intended users.} Capstone students, project supervisors (McMaster faculty and industry
  sponsors), course instructors, and teaching assistants (TAs), across the Software Engineering (SE),
  Computer Science (CS), and Mechatronics (TRON) capstone courses.

  \textbf{Major functionality.} \projname{} covers the lifecycle from project proposal to team project approval.
  Within that boundary the system:
  \begin{itemize}
    \item provides proposal templates for supervisors and for students, so that projects are described
    consistently;
    \item lets instructors review supervisors' project proposals before they are listed, and agree changes
    with the supervisors;
    \item provides a searchable catalog of projects showing which are open, taken, or able to take
    more teams;
    \item lets students and teams create structured profiles of their skills, experience, interests, and work style
    that other students and supervisors can view, indicate whether they are looking for a team,
    and find teammates interested in the same projects;
    \item suggests compatible teammates and suitable projects to students, based on their profiles and preferences
    \item lets student teams express interest in supervisor-proposed projects;
    \item supports communication between all users regarding project proposals, team formations, applications and
    and approvals, ensuring discussions are organized and accessible to relevant parties;
    \item supports comment threads on projects, student posts, and applications, so that questions and
    answers are kept in one place;
    \item lets supervisors and student teams each accept or decline working together, and records when both
    have agreed;
    \item notifies users of events that need their attention, such as new projects, status changes, and replies;
    \item provides supervisors with course process, timeline, and expectation information, and examples of
    past capstone projects, configurable by the course instructor;
    \item gives instructors visibility across courses into projects, teams, and their status, including
    which supervisors' projects were not selected, so that those supervisors can be informed;
    \item provides guidance and automation to help students meet all requirements when submitting their projects for
    approval, and when submitting changes to their project information;
    \item lets instructors and TAs approve, request changes to, or reject a team's project submission and later
    changes to its information;
    \item lets instructors and TAs populate a course with its enrolled students from Avenue to Learn (or by file upload),
    and shows which enrolled students are not yet on a team;
    \item lets instructors configure which features are enabled and disabled for full flexibility
  \end{itemize}

  \textbf{What \projname{} does not do.}
  \begin{itemize}
    \item It does not judge whether a project is feasible, sufficiently complex, or appropriate
    for a capstone course; this remains the responsibility of the course instructor.
    \item It does not make approval decisions. Final approval of teams and projects always rests
    with the course instructor and TAs. Courses may carry out approval inside the platform or in an external process.
    \item It does not resolve intellectual property (IP), confidentiality, or non-disclosure
    questions between students and supervisors.
    \item It does not automatically match supervisors to student-proposed projects. Teams may name a
    supervisor on their proposal or contact one themselves, and supervisors can browse the list of
    student-proposed projects, but \projname{} does not recommend, assign, or maintain an opt-in list
    of supervisors for them.
    \item It does not schedule meetings or provide direct messaging between users. Meetings take place
    outside the platform, and discussion is limited to comment threads on posts and applications.
    \item It does not handle supervision after a project begins, such as feedback requests to
    supervisors, team performance concerns, or grading.
  \end{itemize}

  \textbf{Expected inputs.} Inputs are text-based project and profile information entered by users,
  course enrollment lists, course information, and project status changes made by authorized users.

  \textbf{Expected benefits.} Students can make more informed decisions on which projects to pursue,
  and find compatible teammates; supervisors know who is interested in their projects,
  learn about the students, and receive fewer repeated emails; and instructors spend less time on repetitive
  coordination and gain visibility into the whole process.

  \subsection{Problem Statement}

  \label{sec:problem-statement}

  \plt{Current situation, problem, impact, desired improvement.  You will likely borrow some text from your problem description document.}

  \textbf{Current situation.} Capstone team and project selection is spread across disconnected
  tools, including email, online forms, MS Teams, Avenue to Learn and GitLab.
  Supervisors submit proposals through a form. The SE course instructor, who collects proposals for all
  three courses, reviews them, discusses any changes with the supervisor by email, and edits the list by hand
  before it is distributed to students as a static list.
  Students then form teams informally, mainly through discussion
  forums on Avenue to Learn / Teams and personal contacts, contact supervisors by email, and
  submit their chosen project and team for instructor approval through a course-specific process.
  No single place shows the state of the whole process.

  \textbf{Problems.} The following problems were identified through interviews with stakeholders (see
  \nameref{app:interviews}) and general observation.
  \begin{itemize}
    \item \textbf{Project descriptions are inconsistent and do not set expectations.} Proposals vary
    widely in the level of detail, and very short descriptions put students off. Some of the things
    students want to know include a project's end goal and expected impact. Also, descriptions often do not
    state how much of the project already exists. Supervisors are unsure what a capstone project
    should look like and what a proposal should include, and students who pitch their
    own ideas do not know what a proposal needs. This makes projects difficult to compare and leads
    to mismatched expectations.
    \item \textbf{Student-proposed projects are hard to see.} Students' own project ideas appear only in
    discussion forums, where supervisors cannot see them, including supervisors who would like to
    supervise a student-proposed project. They are not tracked alongside supervisor-proposed projects.
    \item \textbf{There is no visibility of project status.} Students and supervisors cannot see which
    projects are taken or open, or whether a supervisor is willing to take more than one team, and after a
    rejection students do not know which projects remain. New projects and updates are hard to notice, and
    users do not want to have to remember to check for them.
    \item \textbf{Compatible teammates are hard to find.} Students without an existing network rely on
    forum posts or chance. Teammates' project preferences, skills, and work styles are often unknown until
    a team has formed, so teams can disagree about what to build.
    \item \textbf{Supervisors do not know the students' backgrounds.} Supervisors have little structured
    information about the students and teams who contact them, such as their skills, experience, and
    program. They can only gain this information through interviews or rely on outside sources such as
    LinkedIn profiles, which are inconsistent and not always available.
    \item \textbf{Communication during selection is inefficient.} Supervisors receive repeated emails
    from teams, including after a team has been chosen. What one team learns about a project in a meeting
    is not shared with other teams applying for the same project. Nobody can see which teams are in contact with
    which supervisors. There is also no record that a team and a supervisor agreed to work together.
    Students sometimes report that a supervisor agreed when the supervisor has no record of the team, so
    the instructor must confirm agreements separately.
    \item \textbf{Supervisors lack guidance before proposing and responding.} Before proposing a project,
    supervisors receive only a short summary of the course's expectations and process. The full course
    information arrives only after teams and projects are settled, and supervisors want it earlier, along
    with examples of past projects. Supervisors are also unsure how quickly to reply to students and
    whether to speak to every team that contacts them. This leads to misunderstandings about what a
    capstone project should deliver and to many questions to the instructor.
    \item \textbf{Instructors lack visibility across courses.} Instructors cannot see which projects
    students in other capstone courses selected, so they cannot tell which proposed projects were not
    selected. Supervisors whose projects are not selected are not informed, which is a possible
    risk to future project proposals.
    \item \textbf{Instructor review is repetitive and time consuming.} Instructors review each team's submission manually and often
    give the same comments to many teams on simple items, such as missing information, wasting the instructor's time.
    When reviewing project proposals, changes to proposals that are agreed with supervisors by email must then be
    applied to the project list by hand.
    \item \textbf{Records drift after approval.} Team and project information changes after approval (for
    example, titles, supervisors, links, team composition, and TA assignments), but updating the official
    record takes extra steps, so it is often not updated and the instructor's records become out of date.
    \item \textbf{Course enrollment is assembled by hand.} Instructors compare the list of enrolled students against
    team lists by hand to find students who are not yet on a team, and getting enrolled students into a new platform or a
    team workspace is not trivial. Enrollment data lives in Avenue to Learn, which not every course uses.
  \end{itemize}

  \textbf{Impact.} Students lose time early in a project of limited duration, teams end up
  mismatched with their projects or with each other, and course instructors and TAs carry the administrative burden of the
  process. A possible further risk is that supervisors become reluctant to
  propose projects in later years if their projects go unselected or their expectations are not met.

  \textbf{Desired improvement.} All participants share a single, accurate and current source of
  information about projects, supervisors' capacity, teams, and approval status; students can find
  suitable projects and teammates; supervisors can see students’ skills and ideas and receive
  information about the course when they need it; and course instructors keep full control of
  approval decisions while spending less time on repetitive tasks.

  \subsection{Product Vision}

  \plt{A clear and concise statement of the product's purpose and goals.}

  \plt{The goal statements are functional and nonfunctional objectives that system
  under consideration should achieve. Goals provide criteria for sufficient
  completeness of a requirements specification and for requirements pertinence.
  Goals will be refined by requirements.  The goals are written abstractly, with
  a minimal amount of technical language.  They should be understandable by
  non-domain experts.}

  \plt{You will likely borrow from your goal statements in your problem
  description document.}


  \projname{} will be the central place where capstone projects are proposed, discovered, and
  matched with student teams, and where instructors can see and manage the process. Each course
  decides which features it uses and how its approval process is carried out, so the platform can
  be adopted by different courses, departments, and universities.

  The goals of \projname{} are:
  \begin{enumerate}
    \item \textbf{Consistent project information.} Every project, whether proposed by a supervisor or by
    students, is described in a consistent format that makes its objectives, expected impact, required
    skills, current state, and expected outcomes clear.
    \item \textbf{Visibility of availability and updates.} Users can tell which projects are open, taken, or
    able to take additional teams, and are made aware of new projects and changes without having to check
    for them.
    \item \textbf{Easier team formation.} Students can describe their skills, experience, work style, and
    project preferences in a structured profile, find teammates with compatible profiles and preferences,
    and propose projects of their own for others to join.
    \item \textbf{Informed matching.} Students receive suggestions of compatible teammates and suitable
    projects based on their profiles and preferences.
    \item \textbf{Informed supervisors.} Supervisors can see student-proposed projects and the skills and
    experience of the students and teams interested in their projects.
    \item \textbf{Efficient communication during selection.} Questions and answers about a project or
    application are kept in one place, supervisors can see which teams are interested in their projects,
    and fewer repeated emails are needed.
    \item \textbf{Clear agreement between supervisors and teams.} A supervisor's and a team's agreement to
    work together is recorded in the platform and is visible to the instructor.
    \item \textbf{Timely guidance for supervisors.} Supervisors have access to information about the
    capstone course, its timeline, and its expectations, and to examples of past projects, when they
    consider proposing a project, as configured by the course instructor.
    \item \textbf{Oversight for instructors.} Instructors can see projects, teams, supervisors, and their
    status across courses, including projects that were not selected.
    \item \textbf{Instructor-controlled approval with less repetitive work.} Final approval decisions remain
    with the course instructor. The platform supports the project proposal approval process, guiding supervisors to write
    more detailed project proposals and facilitating discussion between the instructor and supervisor.
    The platform supports the team project approval process carried out in the course,
    whether that takes place in the platform or elsewhere, helps students submit complete and correct
    information, and helps keep records current.
    \item \textbf{Configurable and reusable.} Features can be turned on or off, and course-specific
    rules can be configured, so that the platform serves different courses without modification.
  \end{enumerate}

  \subsection{System Constraints}

  \plt{System constraints differ from other type of requirements because they
  limit the developers' options in the system design and they identify how the
  eventual system must fit into the world. This is the only place in the SRS
  where design decisions can be specified.  That is, the quality requirement for
  abstraction is relaxed here.  However, system constraints should only be
  included if they are truly required.}

  \plt{This is where you would mention platform constrains, and licensing
  restrictions.}

  \begin{itemize}
    \item \textbf{Web-based.} \projname{} shall be accessible through current versions of common web
    browsers on desktop, tablet, and mobile devices, and shall not require specialized hardware or
    installation. An internet connection is required.
    \item \textbf{Modular features.} Each major feature shall be able to be enabled or disabled
    independently for each course, so that a course can use only the parts that fit its process.
    \item \textbf{Independent of any one approval tool.} \projname{} shall not depend on a specific
    external tool, such as the GitLab merge request process used by the Software Engineering course,
    to function. It shall support courses that carry out approval in the platform, courses that carry
    it out elsewhere, and, where an adapter exists, courses that synchronize with an external process.
    \item \textbf{Users outside the university.} \projname{} shall support users who do not have a
    McMaster account (such as industry sponsors) alongside users who do.
    \item \textbf{Configurable course rules.} As \projname{} should be extensible to different capstone courses,
    course-specific rules, such as which programs may work together on which projects and the minimum and maximum
    team size, shall be set by the course instructor as configuration and shall not be fixed in the design.
    \item \textbf{Configurable enrollment source.} \projname{} shall obtain a course's enrollment list from Avenue to
    Learn where the course has an Avenue site, and shall also accept an uploaded file, since having an
    Avenue site is optional.
  \end{itemize}

\textbf{Primary Actor}

External Supervisor or Internal Supervisor (Marcus, Dr. Malik)

  \item The supervisor has access to the system.

  \item The supervisor fills in the project title, organization, contact,

    study, confidentiality, and IP concerns.
  \item The supervisor submits the proposal.
  \item The system confirms receipt and gives the proposal the status

  \item The system notifies the instructor of the new proposal.

  \item 3b. The supervisor is not ready to finish: the system saves a draft
    that can be completed later.
  \item 4a. The submission period is closed: the system informs the supervisor
    and does not accept the proposal.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
  \item The proposal is stored with the status ``submitted'' and is visible to
    the instructor.
\end{itemize}

\refstepcounter{ucnum} \label{UC_ApproveTeamProject}
\subsection{\ucref{UC_ApproveTeamProject}: Submit and Approve a Team's Project}

\textbf{Primary Actor}

Student (Priya), Instructor (Dr. Reyes), TA

\textbf{Preconditions}
\begin{itemize}
  \item A team has been formed.
  \item The team and supervisor have both accepted (team-project status ``Agreed''), on a
    listed project or a student-initiated one.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
  \item The student opens the team project submission form for their team.
  \item The system shows the required items: team members, supervisor,
    project, required documents, and a valid project repository.
  \item The student fills in the form and attaches the required documents.
  \item The student submits the team project for approval; the status becomes ``Team project
    submitted''.
  \item The system runs automated checks (e.g., all required fields and
    documents are present, the repository exists and is set up correctly, the
    instructor is added as a collaborator, every member is on exactly one team).
  \item The system forwards the submission, with the results of the checks, to the instructor and TA; the
    status becomes ``Team project under review''.
  \item The instructor or TA review the submission and approves it.
  \item The system changes the team's status to ``Approved'' and notifies the team and
    supervisor.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
  \item 5a. An automated check fails: the system tells the student exactly what
    is missing or invalid, with standard guidance for fixing it, and does not
    forward the submission to the instructor until the issues are fixed. This
    replaces the repetitive comments the instructor writes today.
  \item 7a. The reviewer finds problems the checks cannot catch (e.g., scope
    is too small): the reviewer writes feedback and requests revision. The system sets the status to
    ``Team project changes requested'' and notifies the team, who can
    respond and resubmit (status ``Team project submitted''). The flow returns to step 5.
  \item 7b. The reviewer rejects the submission with a reason: the system sets the status to
    ``Team project rejected'', releases the team's slot (a ``Full'' project becomes ``Open''), and
    notifies the team and supervisor.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
  \item The team's status is ``Approved'', and the data feeds the team composition export (see
    \ucref{UC_ValidateTeams}). The project's own status (``Open'' or ``Full'') is unchanged.
\end{itemize}

\textbf{Related Requirements:} \ref{SR_HumanApproval},
\ref{SR_ReviewDialogue}, \ref{SR_TeamValidity}, \ref{SR_ReduceAdmin},
\ref{SR_TeamSubmissionChecks}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label32}:] The system shall reject all component disable requests if there are pending actions within the component and notify the user of pending actions.
              \rationale{Disabling features may potentially leave the system in a partially invalid state. For example, disabling the project approvals component strands pending project approval requests.}
              \fitcrit{The user interface displays an error message when attempting to disable the project approval component with at least one record present, and the pending records are displayed.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label33}:] The system shall display a timestamp for any displayed records when they were last updated.
              \rationale{Providing users with a timestamp can allow them to judge whether the information they are reading is up-to-date and can contact instructors or supervisors when that is not the case.}
              \fitcrit{Any user authorized to read project proposals and user profiles is able to view a timestamp on all pages.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label34}:] The system shall store pending notifications durably until delivery is verified.
              \rationale{Lost notifications mean that users are not alerted of potentially time-sensitive matters and this can result in missed deadlines and loss of time.}
              \fitcrit{The system being abruptly closed before being able to send a notification sends it after starting back up.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label35}:] The system shall re-verify users for critical, hard-to-reverse actions, such as, but not limited to, updating credentials, any deletion, updating privileges, accepting a project offer, leaving a team, and other final or destructive actions. Re-verification must include at least one of: re-entering credentials, entering an email code, responding to an MFA challenge, and/or responding to an SSO challenge.
              \rationale{Sessions may get stolen or unsecured devices may get compromised. Actions which are difficult to undo should be protected to ensure the actual account holder is performing the action.}
              \fitcrit{The system prompts user to re-enter credentials after requesting to delete a project they proposed.}

              % ---------- Enrollment and TA Roles ---------
              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label36}:] The system shall allow instructors and TAs to import a course's enrollment list from Avenue to Learn, show a preview of the students to be added and the differences from the current list, and apply the import only after the user confirms it.
              \rationale{Populating a course with its students by hand is time consuming, and an unchecked import could wrongly add or exclude students.}
              \fitcrit{An instructor or TA can import an enrollment list and see a preview. No change is applied to the course until the user confirms.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label37}:] The system shall allow instructors and TAs to add students to a course from an uploaded file or by manual entry, including students who join after the initial import.
              \rationale{Having an Avenue site is optional, Avenue may be unavailable, and students sometimes join a course late.}
              \fitcrit{In a course with no Avenue site, the enrollment list can be populated from a file or manually. A student can be added manually after an import.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label38}:] The system shall flag students who are in the course but absent from the latest enrollment list, and shall not remove them from the course or a team until an instructor or TA confirms.
              \rationale{Removing students automatically could leave a team undersized or invalid in the middle of approval.}
              \fitcrit{A student absent from the latest import is listed for review and remains on their team until course staff confirm the removal.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label39}:] The system shall show instructors and TAs the enrolled students who are not on a team.
              \rationale{Instructors currently compare the class list against team lists by hand to find and contact students without a team.}
              \fitcrit{The list contains exactly the enrolled students who are on no team, and it updates as teams change.}

              \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_Label40}:] The system shall allow instructors and TAs to assign a TA to each team, and shall show the assigned TA to the team's members and supervisor.
              \rationale{Supervisors want to know their teams' TAs, and the assignment is currently kept in a manually edited file.}
              \fitcrit{Course staff can assign a TA to a team. The team's members and supervisor see the assigned TA, or ``not yet assigned'' if there is none.}

  \end{itemize}

  \plt{The requirements are given labels so that they can be referenced in other
  parts of the SRS.  The label names should be meaningful mnemonics, not numbers.}

  \section{Data Requirements}
  \label{sec:data-requirements}

  \plt{The Data Requirements section describes what information the system must manage.
  It includes the major data entities, their attributes, and the relationships
  between them.  It also includes a data dictionary that defines the meaning of
  each attribute.}

  This section defines what information \projname{} must manage to support capstone project
  proposals, project discovery, team formation, communication, approval workflows, and 
  course administration. It describes major data entities, their attributes, the meaning of 
  each attribute, and the relationships between them. These data requirements are a proposed
  logical data model based on the functional requirements describing how database technologies
  will store critical data.

  \subsection{Major Data Entities}

  \plt{What information must exist for the system to accomplish its goals?}

  \plt{For each entity, provide a short explanation.}

  \begin{itemize}
    \item \textbf{User (Parent)}: An individual registered in \projname{} including students, supervisors,
    instructors, and TAs.
    \item \textbf{Student (Child of User)}: Students are users that will be selecting a project and a team for the capstone course.
    \item \textbf{Supervisor (Child of User)}: Supervisors are users that manage one or more capstone teams on their project(s) and
    they are able to propose projects themselves which students may work on.
    \item \textbf{Instructor (Child of User)}: Instructors are users who manage one or more capstone course(s) and provide
    feedback and resources to help students succeed in the course.
    \item \textbf{TAs (Child of User)}: TAs assist instructors in course and team management, including approving team
    projects, and are assigned to teams.
    \item \textbf{Course}: A McMaster capstone course supported by Keystone (such as SE, CS, TRON) 
    and includes settings for a capstone course that enables features and implements team formation/
    project selection rules. It contains member and enrollment information, including where the enrollment list comes
    from.
    \item \textbf{Student Profile}: Contains information about a student's background including bio, 
    program, interests, project preferences, skills, experience, work style, and LinkedIn.
    \item \textbf{Team}: A groups of students participating in the same capstone project together.
    \item \textbf{Team Profile}: Contains the collective groups' member bios, collective skills, 
    project interests, goals, and work style.
    \item \textbf{Project}: A supervisor-proposed or student-proposed capstone project that can be 
    described using a title, problem statement/background, objectives, skills/requirements, team 
    deliverables, project impact, supervisor capacity details, level of current completion, relevant course 
    (SE, TRON, CS), industry, information regarding confidentiality and IP concerns, and additional project terms. 
    \item \textbf{Project Application}: Records a student teams interest in supervisor's project including
    a decision from both parties.
    \item \textbf{Thread}: Discussion containing a post or replies associated with a project proposal, team formation,
    or project application.
    \item \textbf{Notification}: Contains information communicated by email related to project updates,
    decisions, discussion activity, urgent deadlines, and outstanding tasks requiring action. 
    \item \textbf{Checklist}: Contains a checklist for the user with checklist items for completion.
    \item \textbf{Course Resource}: Can be a course outline, timeline, guidelines, FAQ, past capstone
    example, or any other course related content that the instructor may post.
  \end{itemize}

  \subsection{Project and Team Status Lifecycle}\label{sec:lifecycle}

  Figure~\ref{fig:lifecycle} shows the statuses a project and the teams working on it pass through,
  and the events that change them. The left side is the lifecycle of a project proposal and its listing
  (one per project). The right side is the lifecycle of each team that works on a project (one per team,
  so a project with capacity greater than one has several). The states in the figure are the only allowed values of the project status and the team-project
  status in the data dictionary, and every other section uses these names exactly.
  \begin{itemize}
    \item \textbf{Project status:} Draft, Proposal submitted, Proposal changes requested, Proposal
    rejected, Proposal withdrawn, Open, Full, and Closed.
    \item \textbf{Team-project status:} Applied, Supervisor Accepts, Team Accepts - Supervisor Pending,
    Agreed, Team project submitted, Team project under review, Team project changes requested,
    Team project rejected, Approved, Approved (change under review), and Declined or withdrawn.
  \end{itemize}
  A team's approval does not change the project's status. A listed project is Open or Full
  depending only on capacity.

  \begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{ProjectLifecycleStateDiagram}
    \caption{Project and team status lifecycle}\label{fig:lifecycle}
  \end{figure}

  \textbf{Capacity.} Let $C$ be the supervisor's capacity for the project and $R$ the number of
  slots reserved. A listed project is \emph{Open} while $R<C$ and \emph{Full} when $R=C$. A team's
  application, and a team's acceptance on its own, do not use a slot. A slot is reserved when the
  supervisor accepts a team (the state \emph{Supervisor Accepts}, or \emph{Agreed} when the team had
  already accepted), and $R$ increases by one. A reserved slot is released, only if one was
  reserved, when that team is declined or withdraws, when its team project is rejected, or when it
  dissolves after approval. Releasing a slot, or raising $C$, makes a Full project Open. A project
  becomes \emph{Closed} when the selection period ends, whether it is Open or Full. A Closed project
  with no approved team is \emph{unselected} (see \ucref{UC_FollowUpUnselected}).

  \textbf{Review.} Proposals and team projects are each reviewed by the course instructor, who can approve,
  request changes (the proposer or team then resubmits), or reject. In an \emph{external} approval mode the
  instructor or TA records the outcome instead of the platform running the review (see \rref{FR_Label19}).

  \textbf{Changes after approval.} A team may submit a change to an approved project. The team's status
  stays \emph{Approved} (shown as \emph{Approved, change under review}), and the original approval
  remains in effect, until the instructor accepts or rejects the change. Either outcome returns the
  team to \emph{Approved}; accepting the change also updates the record.

  \subsection{Privacy and Data Retention}

  \plt{Discuss storage, retention, deletion, privacy controls,
    consent, encryption, and compliance requirements.}
  The following are requirements how the system will manage data to ensure security and privacy in its lifecycle.

  \subsubsection{Storage}
  \begin{enumerate}
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label1}:] The system shall securely store its data in a centrally managed backend system accessible by authorized actors
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label2}:] The system shall store data based on the Data Entity definitions in Sections 7.1 and 7.2
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label3}:] The system shall maintain accuracy and consistency of stored information ensuring it is up-to-date based on real-time actions
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label4}:] The system shall backup all data every 2 weeks to reduce the risk of data loss from system failures or deletions
  \end{enumerate}

  \subsubsection{Data Retention and Deletion}
  \begin{enumerate}
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label5}:] The system shall retain instructor and course related data to be used the following year until the instructor has taken action to make the deletions.
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label6}:] The system shall allow restricted deletion of any data only by authorized administrators that are managing the application with access to the database.
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label7}:] The system shall allow authorized users to delete content that they created or are specifically managing on the application including their own personal information as well as make edits.
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label8}:] The system shall automatically delete student information at the end of the capstone period
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label9}:] The system shall only retain completed project information past the capstone period if the team has consented
  \end{enumerate}

  \subsubsection{Privacy Controls}
  \begin{enumerate}
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label10}:] The system shall implement Role-Based Access Control to allow users to perform read, write, delete, and modify actions based on their role (e.g. Students may not modify other projects that do not belong to them while instructors can edit any project in their course)
  \end{enumerate}

  \subsubsection{Consent}
  \begin{enumerate}
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label11}:] The system shall inform users about all information including personal data that is being retained and used for recommendations
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label12}:] The system shall not disclose any data to unauthorized external parties
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label13}:] The system shall provide a Privacy Notice providing users with information related to data collection, use, storage, and retention
    \item[DPR\refstepcounter{dprnum}\thedprnum \label{DPR_Label14}:] The system shall allow consent withdrawal
  \end{enumerate}

  \section{Non-Functional Requirements}

  \label{sec:non-functional-requirements}

  \plt{You may have to add other NFRs.}

  \plt{List your nonfunctional requirements.  You may consider using a fit
  criterion to make them verifiable.}

  \plt{The goal is for the nonfunctional requirements to be unambiguous, abstract
  and verifiable.  This isn't easy to show succinctly, so a good strategy may be
  to give a ``high level'' view of the requirement, but allow for the details to
  be covered in the Verification and Validation document.}

  \plt{An absolute requirement on a quality of the system is rarely needed.  For
  instance, an accuracy of 0.0101 \% is likely fine, even if the requirement is
  for 0.01 \% accuracy.  Therefore, the emphasis will often be more on
  describing now well the quality is achieved, through experimentation, and
  possibly theory, rather than meeting some bar that was defined a priori.}

  \plt{You do not need an entry for correctness in your NFRs.  The purpose of the
  SRS is to record the requirements that need to be satisfied for correctness.
  Any statement of correctness would just be redundant. Rather than discuss
  correctness, you can characterize how far away from the correct (true)
    solution you are allowed to be.  This is discussed under accuracy.}

  \section{Rationale}

  \plt{Provide a rationale for the decisions made in the documentation.  Rationale

  \subsection{Scope}

  The scope was decided based on an estimate of what stakeholders need and what would be considered nice-to-have features, as described in Section~\ref{sec:scope}.

  Keystone focuses on project proposals, discovery, team formation, visibility, and project approvals rather than 
  the entire capstone lifecycle. Features such as automated project evaluations, AI-features, full course management, 
  post-approval supervision, meeting scheduling, messaging, and intellectual property dispute resolution were excluded to 
  keep the project scope manageable and most were not desirable implementations for the stakeholders or were simply 
  overkill for this project. Also, too much automation was undesirable by stakeholders as instructors prefer to be in 
  control of approving projects and manually providing feedback.


  \subsection{Functional Requirements}

  Each functional requirement's rationale can be found underneath the corresponding requirement in Section~\ref
  {sec:functional-requirements}. The functional requirements were generally derived from stakeholder 
  requirements, as demonstrated in Section~\ref{sec:traceability-matrices}. Therefore, the core functionality of 
  the system is determined by the needs of its users. Functional requirements without direct stakeholder 
  traceability primarily address underlying system and security needs necessary to provide a reliable platform.

  \subsection{Non-Functional Requirements}

  Each non-functional requirement's rationale can be found underneath the corresponding requirement in 
  Section~\ref{sec:non-functional-requirements}. These requirements establish the quality standards necessary for 
  Keystone to serve its stakeholders effectively. Requirements such as access, availability, accessibility, and 
  usability ensure that stakeholders can use the system efficiently and without significant challenges. While 
  functional requirements define the system's capabilities, non-functional requirements provide measurable goals 
  for its quality, robustness, and performance.

  \subsection{Data Requirements}

  The data requirements in Section~\ref{sec:data-requirements} were established to support the functional 
  requirements while maintaining consistent and accurate information across the platform.

  \begin{itemize}
      \item \textbf{User Child Entities:} A parent User entity was defined with child Student, Supervisor, 
      Instructor, and TA entities to represent shared information while distinguishing role-specific attributes.
      This was especially necessary when restricting entity relations (e.g. only Students belong to a team)
      \item \textbf{Entity Choices:} They come directly from the functional and stakeholder requirements as they determine all 
      of the objects needed to represent the required actors and features in the system.
      \item \textbf{Course Configuration:} Course-specific settings and rules are associated with the Course entity to support 
      different capstone workflows without requiring structural changes to the data model.
      \item \textbf{Data Integrity:} Relationships and constraints were established to prevent invalid team memberships, 
      duplicate project assignments, and inconsistent records.
      \item \textbf{Data Privacy and Retention:} These requirements were designed to ensure that a user's sensitive information
      such as email and any data about their project remains secure in our backends and in compliance with Privacy Protection
      policies. Keeping data encrypted can do this and RBAC keeps everyone's access adhering to the principle of least privilege.

  \end{itemize}

  \subsection{AI Requirements}
  \label{rat:ai-requirements}

  Implementing an AI-based solution is primarily outside the core project scope and is instead considered a stretch goal. The 
  system does not require training an AI model to fulfill its primary functionality.

    He receives the list of students in the capstone courses, manually marks off those who are in a group, and contacts
    the rest. He tries not to force students into groups, so some students are delayed in getting a group. One student
    joined a group very late, and the situation was handed to the undergraduate advisor.
    \item[TI\refstepcounter{tin}\thetin \label{TI_Populate}]
    Teams channels must be created and populated from Avenue or added manually, and students are removed if they are
    not on Avenue. Populating a platform with student information is not trivial. Having an Avenue course is optional;
    an instructor requests one and it is then created.
    \item[TI\refstepcounter{tin}\thetin \label{TI_CrossProgram}]
    SE students on TRON projects are treated as TRON students, and their grades are sent to the SE instructor. TRON
    students cannot join software-only projects. ECE students on TRON projects must be graded by an ECE professor to
    show their involvement. Cross-discipline capstones, such as iBioMed, need additional considerations and
    involvement from professors, and accreditation is a concern.
    \item[TI\refstepcounter{tin}\thetin \label{TI_Projects}]
    Projects are collected over the summer through the SE instructor and his contacts, and are kept in a LaTeX
    document. Many TRON projects are student-proposed, and student-proposed projects are often high quality and
    people-centred.
    \item[TI\refstepcounter{tin}\thetin \label{TI_StudentOwned}]
    The capstone is student-centred. Students own the project even if stakeholders are involved, and the only rule is
    that students must be able to talk about it (presentations, EXPO). Supervisor-only deliverables are secondary and
    should not overwhelm students. He sends the supervisors a list of the previous year's deliverables.
    \item[TI\refstepcounter{tin}\thetin \label{TI_Meetings}]
    Teams meet in person during class time.
    \item[TI\refstepcounter{tin}\thetin \label{TI_OpenQuestion}]
    Open question: how involved the platform will be in the capstone process.
\end{itemize}

  \subsection{Appendix B: Development Plan}

  \plt{This section is optional.  It is used to explain the plan for developing
  the software.  In particular, this section gives a list of the order in which
  the requirements will be implemented.  In the context of a course  this is
  where you can indicate which requirements will be implemented as part of the
  course, and which will be ``faked'' as future work.  This section can be

  requirements that will be implemented for ``phase 1'', ``phase 2'', etc.}

  \section{Development Plan}

Requirements are grouped into phases. Phase 1 creates the smallest end-to-end
path through the lifecycle (see Figure~\ref{fig:lifecycle}), so that a project can be proposed, approved, listed, selected, and finally approved for a
team. Priority within a phase follows the instructor's biggest pain point(repetitive review of team submissions) 
and then the dependencies between features.

\subsection{Phase 1: Core Workflow (implemented in the course)}
\begin{itemize}
  \item Importing course enrollment from Avenue to Learn, with file upload as an alternative, and a list
    of enrolled students who are not on a team (\ucref{UC_ImportEnrollment}; \ref{SR_Enrollment}). Team validation
    (\ucref{UC_ValidateTeams}) needs to know who is enrolled, so this comes first.
  \item Supervisor proposal submission with a structured template, and
    instructor approval before a project is listed
    (\ucref{UC_SubmitProposal}, \ucref{UC_ReviewProposal};
    \ref{SR_ProposalTemplate}, \ref{SR_OptionalFields}, \ref{SR_HumanApproval}).
  \item Browsing projects with a visible status, and team selection
    (\ucref{UC_BrowseProjects}, \ucref{UC_SelectProject};
    \ref{SR_BrowseProjects}, \ref{SR_ProjectStatus}).
  \item Team project submission with automated checks, and instructor and TA review
    with iterative feedback (\ucref{UC_ApproveTeamProject};
    \ref{SR_TeamSubmissionChecks}, \ref{SR_ReviewDialogue}, \ref{SR_TAApproval}). This is the
    highest-value feature for the instructor, so it is part of the first
    working version.
  \item Validated team composition export
    (\ucref{UC_ValidateTeams}; \ref{SR_TeamValidity}, \ref{SR_ReduceAdmin}).
\end{itemize}

\subsection{Phase 2: Communication and Visibility (implemented in the course)}
\begin{itemize}
  \item Email notifications for status changes and tasks, and a checklist of
    required actions (\ucref{UC_NotifyChecklist}; \ref{SR_StatusNotify},
    \ref{SR_PushNotify}, \ref{SR_Checklist}).
  \item Team profiles visible to supervisors, and team contact details
    (\ucref{UC_TeamProfile}, \ucref{UC_ViewTeam}; \ref{SR_StudentProfiles},
    \ref{SR_TeamContacts}).
  \item Course schedule and timelines (\ucref{UC_ViewTimelines};
    \ref{SR_CrossCourseTimelines}).
  \item Identifying unselected projects
    (\ucref{UC_FollowUpUnselected}; \ref{SR_UnselectedProjects}).
\end{itemize}

\subsection{Phase 3: Extended Features (implemented if time allows)}
\begin{itemize}
  \item Student-initiated project proposals
  (\ucref{UC_ProposeOwnProject}; \ref{SR_StudentProposals}). Phase 1 already
    provides most of the approval flow, so this mainly adds a proposal path, a
    student-proposed project list that supervisors can browse, and an optional field
    for naming a supervisor.
  \item Guidelines, FAQ, examples of past projects, and early access to course
    information (\ref{SR_ProposalGuidance}, \ref{SR_CourseInfoEarly}). This
    is mostly content, so it can be added without changing the core system.
  \item Supervisor capacity limits (a count of teams per supervisor) and
    related checks.
\end{itemize}

\subsection{Future Work (not implemented, or faked for the demo)}
\begin{itemize}
  \item (\ref{SR_SinglePlace}) a single place for all capstone coordination,
    is addressed in part by the above, but full replacement of external tools
    (e.g., email, calendar, meeting tools) is future work.
  \item Meeting notes, searchable communication history, and suggested
    meeting schedules are not in the current requirements. They would be added
    after the core system is stable.
  \item Matching teams to projects by skills and interests is future work. It
    is optional and the instructor wants it to be switchable.
  \item Support for other capstone courses or universities (modularity) is a
    design goal, but a second deployment is future work.
\end{itemize}

\subsection{Faked or Simplified for the Course}
\begin{itemize}
  \item Email delivery may use a test mailbox or log messages instead of
    reaching real inboxes during demos.
  \item Authentication may use a simplified sign-in for the demo, with real
    integration with university accounts as future work.
  \item Data may be seeded with example projects, teams, and supervisors
    instead of imported from the existing forms and spreadsheets.
\end{itemize}
