\section{General Information}
\label{sec:general}

\subsection{Summary}

The software under test is \projname{}, a web-based capstone project management system for the Software Engineering (SE), Computer Science (CS), and Mechatronics (TRON) capstone courses. \projname{} covers the lifecycle from project proposal to team project approval. Its main functions are:
\begin{itemize}
  \item structured project proposals by supervisors and student teams, with instructor review before a project is listed;
  \item a searchable project catalog showing project status and supervisor capacity;
  \item student and team profiles, team formation under course-specific rules, and teammate and project recommendations;
  \item team applications to projects, supervisor and team acceptance, and comment threads attached to projects and applications;
  \item team project submission with automated checks, and approval by instructors and TAs, either in the platform or recorded from an external process;
  \item course enrollment import from Avenue to Learn or file upload, validated team composition export, and email notifications and checklists;
  \item role-based access control, authentication through McMaster SSO or another trusted provider, and audit logging.
\end{itemize}
The requirements being verified are listed in the SRS \citep{SRS}.

\subsection{Objectives}


The objectives are ordered by priority, based on the risks identified in the SRS: errors in the approval workflow affect course records, errors in access control expose student data, and a hard-to-use platform will not be adopted by supervisors.

\textbf{In scope.}
\begin{enumerate}
  \item \textbf{Functional correctness.} Build confidence that the functional requirements (\rref{FR_SupervisorProposal} to \rref{FR_AssignTA} in the SRS) are met, especially the project and team-project status lifecycle, supervisor capacity (slot reservation and release), team formation rules, submission validation, enrollment import, and external supervisor verification and scoping.
  \item \textbf{Access control and privacy.} Demonstrate that users can only see and change what their role and course permit, and that data is protected in transit and at rest (\nfrref{NFR_Authenticate}, \nfrref{NFR_Authorize}, \nfrref{NFR_EncryptTransit}, \nfrref{NFR_EncryptRest}, \dprref{DPR_RoleBasedDataPermissions}, \dprref{DPR_VisibilityMatrix}, \dprref{DPR_EncryptionAtRest}).
  \item \textbf{Usability.} Demonstrate that first-time users in the main roles (students, TAs, and professors) can complete their primary tasks within the usability time limit, and find the platform intuitive and easy to use (\nfrref{NFR_UsabilityFirstSuccess}, \nfrref{NFR_LearnUnassisted}).
  \item \textbf{Performance and installability.} Demonstrate that the system meets its latency target under the specified load, and that an IT professional can deploy it from the deployment guide within the time limit (\nfrref{NFR_PerfTail}, \nfrref{NFR_PeakUsers}, \nfrref{NFR_DeployUnassisted}).
  \item \textbf{Portability and accessibility.} Demonstrate that the system works on the target browsers and in Docker, and passes an automated accessibility audit (\nfrref{NFR_Browsers}, \nfrref{NFR_Container}, \nfrref{NFR_AccessibilityWCAG}).
\end{enumerate}

\textbf{Out of scope.}
\begin{itemize}
  \item \textbf{Quality of recommendations.} We will test that recommendations are produced and displayed (\rref{FR_TeamRecommend}), but not whether they are good matches. Recommendation quality is a stretch goal in the SRS, and judging it would need a study with real students.
  \item \textbf{External systems.} We assume that McMaster SSO, Avenue to Learn, the email service, and third-party libraries have been verified by their developers. We test our handling of their failures (for example, an unavailable Avenue), not their correct operation. Following the SRS Development Plan, email delivery and authentication may be simulated during the course.
  \item \textbf{Availability over time.} The availability criterion is measured over a long window (see the SRS), which cannot be observed within the course timeline. We will verify that the health check works and that the system meets the target over the period that the demo allows.
  \item \textbf{Maintainability.} We will review the likely changes in the SRS against the design, but will not measure the actual effort of making changes.
  \item \textbf{Features not implemented.} Requirements that the SRS Development Plan marks as future work, or as Phase 3 and not completed, will not be tested.
  \item \textbf{Formal verification.} We do not plan formal proofs.
  \item \textbf{Industry sponsors.} The usability test does not include external supervisors from industry, who have no McMaster account and are the least familiar with the course. Professors in the test represent internal supervisors and instructors. Findings about external supervisors will need follow-up testing if one becomes available.
\end{itemize}

\subsection{Custom Documents}

This project has two Custom Documents: a usability testing report and an interview report.

The \textbf{usability testing report} records the results of the usability test described in Section~\ref{sec:usability-tests} and supports the Usability NFR in the SRS. In the test, we observe TAs, students, and professors using \projname{} to complete the primary tasks of their roles, to judge whether the platform is intuitive and easy to use without training. The report covers the participants and their roles, the tasks given, completion times, problems and points of confusion observed, and the changes made as a result.

The \textbf{interview report} records the stakeholder interviews that the requirements were derived from: students, external and internal supervisors, and the SE, TRON, and CS course instructors. It contains the interview notes, the requirements and design decisions each note led to, and the stakeholder feedback on the SRS and on the working system. It supports validation by checking that \projname{} solves the problems stakeholders described, and the SRS (Appendix A) summarizes it.

\subsection{Relevant Documentation}

The following documents define what is verified and how the verification is organized.
\begin{itemize}
  \item \textbf{Software Requirements Specification (SRS)} \citep{SRS}. This is the main source for this plan. System tests are derived from its functional requirements, nonfunctional requirements and fit criteria, use cases, and data requirements. The SRS defines the symbolic constants (such as the number of concurrent users and the latency limit) that the nonfunctional tests use, and its traceability matrices will be extended to link each requirement to the tests in this document.
  \item \textbf{Hazard Analysis} \citep{HazardAnalysis}. It identifies hazards such as failures of the external approval system and access control failures, and the safety and security requirements that follow from them. Tests are added for each of these requirements.
  \item \textbf{Problem Statement and Goals} \citep{ProblemStatement}. It records the problems and goals that validation checks against. Validation with stakeholders asks whether the system solves these problems, not only whether it meets the SRS.
  \item \textbf{Development Plan} \citep{DevelopmentPlan}. It defines the tools and workflow (such as version control, continuous integration, and linting) that the automated testing in this plan relies on.
  \item \textbf{Module Guide (MG) and Module Interface Specification (MIS)} \citep{MG, MIS}. These will define the modules and interfaces that the unit tests in this plan target. The unit test sections will be completed after the design is finished.
\end{itemize}

  \paragraph{Handling review feedback.} All reviews in this plan follow one process, which is not repeated in each subsection.
  Every finding from a review, walkthrough, inspection, or stakeholder meeting is recorded as a GitHub issue with the
  \emph{Verification} label (and the \emph{Documentation} or \emph{Bug} label where relevant), and is assigned to a team
  member.
  The assignee fixes the finding on a branch and opens a pull request that references the issue. The pull request goes through the
  normal pull request review described in the Development Plan \citep{DevelopmentPlan}, and the issue is closed only after the pull
  request is merged and the reviewer who raised the finding, or a teammate, confirms that the change addresses it.
  A finding that the team decides not to act on is closed with a written reason.

  \subsection{SRS Verification}
  \label{sec:srs-verification}

  The SRS \citep{SRS} is verified in four steps before it is treated as the basis for design and testing.

  \begin{enumerate}
    \item \textbf{Internal review.} Each team member reviews the sections that they did not write,
    using the SRS checklist from the course. The reviewer also checks the qualities that the SRS
    template asks for: unambiguous, consistent, complete, validatable, and abstract.
    The documentation and technical QA member then checks traceability:
    every stakeholder requirement maps to a use case and a functional requirement,
    every functional requirement maps to a stakeholder requirement or a nonfunctional requirement,
    every ``Traces To'' entry in the Hazard Analysis \citep{HazardAnalysis} names a requirement that exists in the SRS,
    and every requirement has a fit criterion that can be tested.
    \item \textbf{TA review.} Chris Schankula reviews the SRS and provides feedback.
    \item \textbf{Peer review.} Classmates review the SRS using the Peer Review issue template, with the SRS checklist and the rubric.
    \item \textbf{Validation with the instructors.} Reviewing the SRS ourselves cannot show that it matches how the courses really work,
    so Dr. Smith validates the facts that only he can confirm, through a structured walkthrough and a checklist. These are described below.
  \end{enumerate}

  \textbf{Walkthrough and checklist with Dr. Smith.} We hold one 45 minute session with Dr. Smith,
  in the first supervisor meeting after the SRS is submitted and before the design document is started.
  The team presents instead of asking him to read the SRS, because the SRS is long and the questions
  that matter are about the use cases and the lifecycle. The agenda is in Table~\ref{tab:walkthrough-agenda}.
  We walk through the project and team-project status
  lifecycle and four use cases: \texttt{UC\_ReviewProposal}, \texttt{UC\_ApproveTeamProject},
  \texttt{UC\_ImportEnrollment}, and \texttt{UC\_FollowUpUnselected}.
  These are the ones where the instructor's own process and decisions matter most.
  For each one, the presenter reads the main success scenario and the alternative flows and asks the
  targeted questions listed in Appendix~\ref{app:walkthrough}.
  Dr. Smith then marks a short checklist of the statements in the SRS that only he can confirm, each as correct,
  needs a change, or unsure. The agenda, the questions, and the checklist are in Appendix~\ref{app:walkthrough}.
  His answers are recorded in the Supervisor Meeting issue, and every ``needs a change'' or ``unsure'' answer
  becomes a Verification issue as described above.

  \subsection{Design Verification}
  \label{sec:design-verification}

  The design documents are the Module Guide and the Module Interface Specification \citep{MG, MIS}. They are verified as follows.

  \begin{enumerate}
    \item \textbf{Checklist review.} Teammates, the TA, and classmates review the documents using the
    course's MG and MIS checklists and the rubric.
    \item \textbf{Requirements coverage check.} The documentation and technical QA member builds a table
    mapping every functional requirement and every safety and security requirement to the module(s) that satisfy it,
    and every module to the requirement(s) it exists for.
    \item \textbf{Hazard scenario review.} For each hazard in the FMEA of the Hazard Analysis \citep{HazardAnalysis},
    the team identifies the design element that mitigates it and checks that the mitigation is in the
    design and not only in the requirements. The review gives extra attention to the places where
    the design is most likely to fail such as the status lifecycle and slot reservation logic,
    simultaneous requests (race conditions), and the enforcement of visibility rules on every read path.
    \item \textbf{Design walkthrough with Dr. Smith.} We walk through the module decomposition with him using
    scenarios, because modularity is his main design concern.
    Example scenarios are: an instructor disables a feature, a course uses external instead of
    in-platform approval, a course changes its team size rules after teams have formed,
    and a second university uses \projname{} with a different enrollment source.
    For each scenario, we trace which modules change and which do not, and he judges whether the result is acceptable.
  \end{enumerate}

  \subsection{Verification and Validation Plan Verification}
  \label{sec:vnv-verification}

  This plan is verified in the following ways.

  \begin{enumerate}
    \item \textbf{Review.} Teammates, the TA, and classmates review the plan using the course's VnV plan
    checklist and the rubric.
    \item \textbf{Coverage check.} We confirm that every in-scope requirement in the SRS has at least one test,
    using the traceability table in this document. Requirements that carry the
    most risk (the status lifecycle and slot reservation, team size limits, role-based visibility,
    and enrollment import) must have more than one test, so that a passing test suite gives real confidence.
    \item \textbf{Hazard check.} For each hazard in the Hazard Analysis, we ask which test would fail if
    the hazard occurred. A hazard with no such test is a finding.
    \item \textbf{Validation review with Dr. Smith.} He reviews only the software validation plan
    (Section~\ref{sec:validation}) and the usability test protocol, because this is where his input is most useful.
    \item \textbf{Mutation testing (planned extra, high-risk areas only).} To check that the automated tests
    can detect faults, the team will run mutation testing on the highest-risk backend modules only. This includes
    the status lifecycle and slot reservation logic, the team formation rule checks, and the role-based visibility checks.
    The tool is mutmut. The run happens before the Revision 0 demo and before the final demo.
    Surviving mutants are examined, and each one that shows a missing test becomes a Verification issue.
    If time runs short, mutation testing is dropped without affecting any other part of this plan.
  \end{enumerate}

  \subsection{Implementation Verification}
  \label{sec:impl-verification}

  Implementation verification combines dynamic testing, static analysis, and a code walkthrough.

  \subsubsection*{Dynamic testing}

  \begin{itemize}
    \item \textbf{Unit tests (owner: Ayush).} Backend unit tests with pytest cover the API endpoints and the
    core logic. Frontend unit tests with Jest cover components, including form validation and the display of statuses.
    Test design follows the guidance in the Development Plan \citep{DevelopmentPlan},
    including boundary values and expected failures.
    The target is about 80\% statement coverage. Section~\ref{sec:unit-tests} describes the unit tests in detail.
    \item \textbf{Integration tests (owner: Ahmed).} These run the backend against a real PostgreSQL database
    in Docker, to test the transactions, constraints, and locking that the safety requirements depend on.
    The email service is replaced by a local test mail server (for example Mailpit), so tests can check what is sent,
    to whom, and how often. Avenue to Learn is replaced by a stub that can return a valid list,
    a malformed list, a duplicate entry, or no response, so that we test our handling of its failures,
    as the General Information section describes. Authentication providers are simulated in the same way.
    \item \textbf{End-to-end tests (owner: Andrew).} Playwright tests drive the real application in a
    browser through the most important use cases for each role.
    They run in Chrome, Firefox, and Safari (WebKit) at the three screen widths named in the SRS, and include
    an automated accessibility audit (axe-core) of every page in Chrome.
    \item \textbf{Performance tests (owner: Waqar).} A load test with Locust simulates the number of
    concurrent users, think time, and 95th percentile latency limit set in the nonfunctional requirement
    \texttt{NFR\_PerfTail} of the SRS. The load test runs before milestones, not on every pull request,
    because it is slow and needs a full deployment. A first baseline run is done once the project catalog and
    application flow exist, and a run is done before each milestone from the Revision 0 demo onward, so that
    slow queries are found early.
  \end{itemize}

  \subsubsection*{Static verification}

  \begin{itemize}
    \item \textbf{Static analyzers and linters.} Ruff and ESLint run on all code,
    as in the Development Plan \citep{DevelopmentPlan}. We add a static type checker for the
    backend (mypy) and strict mode in TypeScript, because type errors in status and role handling are a
    likely source of faults. SonarQube analyzes code quality and coverage reports.
    Dependency audits (\texttt{pip-audit} and \texttt{npm audit}) check for known vulnerabilities.
    \item \textbf{Code walkthrough.} Before the Revision 0 demo, the team and the TA hold a walkthrough of the
    modules where a fault would cause the most harm: the status lifecycle and slot reservation logic,
    the visibility and role checks (including the external supervisor limits),
    and the notification queue and enrollment import.
    The author of a module presents it, and the other participants inspect it against a short checklist:
    the code follows the module interface specification, multi-step changes happen in one transaction,
    every read path checks permissions on the server, errors are handled explicitly,
    course rules are read from configuration and not written in the code, and each branch has a test.
    The session is recorded in a Team Meeting issue, and findings follow the process above.
    This is in addition to normal pull request review.
  \end{itemize}

  \subsection{Software Validation}
  \label{sec:validation}

  Validation checks that we are building the right product:
  one that solves the problems in the Problem Statement \citep{ProblemStatement},
  and not only one that meets the SRS. It is done with stakeholders in the following ways.
  The details of each will be given later, in the usability test protocol (Section~\ref{sec:usability-tests})
  and the Usability Testing Report.

  \begin{itemize}
    \item \textbf{Usability testing.} Students, TAs, and professors complete the primary tasks of their
    roles, as described in the Custom Documents section.
    \item \textbf{Stakeholder interviews.} We interview students, supervisors, and instructors again after
    the requirements and the first working version are available, to check that the platform addresses what they told us.
    \item \textbf{Demonstrations.} The Proof of Concept demo, the Revision 0 demo, and the final demo are used as
    validation points with Dr. Smith. After the Revision 0 demo, we also demonstrate the platform to
    Dr. Moradi and Dr. Wassyng and students.
  \end{itemize}

  As the General Information section states, external supervisors from industry are not part of the
  usability test.

\subsection{Usability Survey Questions}
\label{app:usability-survey}

Participants complete this survey after attempting their assigned task. \\

\noindent\textbf{Rating Questions}

\noindent Participants rate each statement on a 1--5 scale, where 1 is
\textbf{strongly disagree} and 5 is \textbf{strongly agree}.

\begin{enumerate}
  \item I understood what I was expected to do.
  \item I could find the information or action I needed.
  \item The labels and instructions were clear.
  \item The system behaved as I expected.
  \item I could complete the task without help.
  \item I would feel confident using this system for the same task.
\end{enumerate}

\noindent\textbf{Open-Response Questions}

\noindent Participants answer each question in their own words.

\begin{enumerate}
  \setcounter{enumi}{6}
  \item What was the most confusing part of the task?
  \item What, if anything, would you change to make the task easier?
\end{enumerate}

\subsection{Deployment Guide}

This guide describes how to deploy \projname{} on a Linux server with Docker
installed. It is used in \hyperref[T-NFR-INST-1]{\textbf{T-NFR-INST-1}}. It is a
draft, and file and variable names will be updated to match the implementation.
Replace values in angle brackets with those for your deployment.

\begin{enumerate}
  \item Connect to the server:
\begin{verbatim}
ssh <ssh-user>@<server-address>
\end{verbatim}
  \item Get \projname{}, enter its directory, and check out the release tag
  provided with this guide (in the form \verb|v<major>.<minor>.<patch>|):
\begin{verbatim}
git clone https://github.com/Ayushpatel2026/Keystone.git
cd Keystone
git checkout <release-tag>
\end{verbatim}
  \item Create the configuration file from the template:
\begin{verbatim}
cp .env.example .env
\end{verbatim}
  \item Open \texttt{.env} and set the following values:
\begin{verbatim}
ADMIN_EMAIL=<admin-email>
ADMIN_PASSWORD=<admin-password>
TLS_CERT_PATH=<certificate-path>
TLS_KEY_PATH=<key-path>
\end{verbatim}
  \item Build and start the system:
\begin{verbatim}
docker compose up -d --build
\end{verbatim}
  \item Check that all containers are running:
\begin{verbatim}
docker compose ps
\end{verbatim}
  \item Open \verb|https://<server-address>| in a browser and sign in with
  the admin credentials.
\end{enumerate}
